# Mission Reflection — Laboratory 4

Deploying Nginx with Docker made the difference between VMs and containers concrete rather than theoretical. Spinning up a VM means booting an entire guest operating system — allocating virtual CPU, RAM, and disk, then waiting minutes for the OS itself to initialize before any application software can even start installing. With Docker, docker run had Nginx serving traffic in seconds, because the container isn't booting an OS at all — it's just starting an isolated process that shares the host's kernel. That single difference is why containers are so much lighter on resources: there's no duplicated OS layer eating RAM and disk for every instance.

Port mapping (-p 8080:80) is necessary because a container's internal network is isolated from the host by default. Nginx inside the container is listening on port 80, but that port only exists inside the container's own network namespace — the host machine has no direct route to it. The -p 8080:80 flag creates a bridge, forwarding traffic that arrives on the host's port 8080 into port 80 inside the container. Without it, curl http://localhost:8080 would simply fail to connect, even though Nginx is running perfectly well inside the container.

Running docker rm after stopping the container permanently deletes the container's writable layer — any files created or changed inside that container while it was running are gone. This is what makes containers ephemeral by design: they're meant to be disposable, stateless units. That's also why production setups use volumes or bind mounts for anything that needs to persist, rather than relying on the container's own filesystem.

Containerization changes the developer/operations relationship by giving both sides a shared, portable unit of deployment. A developer can build and test in a container locally, and the exact same image runs in staging and production — eliminating the "it worked on my machine" problem, because environment differences that plague VM deployments are baked into the image itself. This is a big part of why DevOps and containers grew up together: containers make continuous integration and deployment pipelines far more reliable, since what's tested is exactly what's shipped.
